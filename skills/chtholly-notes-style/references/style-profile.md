# 个人博客风格

## 标题与标签

- H1 直接写问题、算法名称或具体做法，例如 `# K. Maximum Rating`、`# fmtlog 跨 DSO 崩溃与日志丢失`。
- H1 下一行只写标签式短语，例如 `数据结构。`、`贪心。`、`fmtlog，DSO，符号可见性。`。
- 标签通常由技术名、数据类型或问题类型组成，不使用完整句子。
- 文件名为 `主题.md`，主题里不堆错误信息、反引号和冒号。

## 叙述方式

- 默认使用第一人称或省略主语，少用“本文将”“我们需要”“可以看到”。
- 用短句推进，一段通常只解决一个小问题，逻辑词偏向“考虑、发现、后来、于是、不过、其实、注意、也可以”。
- 先写现象或直觉，再写尝试和修正。允许出现“一开始觉得”“当时没想清楚”“后来重新看源码才发现”。
- 对不确定内容保留猜测语气，例如“可能是”“应该是”“暂时还没找到”“这里不太确定”。
- 可以轻松一点，但不刻意卖萌。删除线只用于真实的自嘲或补充，不为模仿风格而添加。
- 不追求每一段都有总结句，也不把所有过程整理成整齐的三段式或并列结构。

## 技术内容

- 算法题通常先点明核心观察，再说明为什么这样做，最后补复杂度或容易写错的位置。
- debug 记录通常从原始报错或异常现象开始，随后写最初判断、失败尝试、源码证据、修改和现在的状态。
- 优化记录通常先写旧做法和瓶颈，再写新做法、边界条件以及性能或行为上的代价。
- 代码用于说明关键实现，不贴与结论无关的完整工程文件。
- 大段代码使用：

````html
<details>
<summary>点击查看代码</summary>

```cpp
// code
```
</details>
````

- 优化、算法和 debug 记录里，如果代码已经有比较完整的解决或实现方案，在正文结束后单独附一份：引导语写清是什么代码，例如 `完整的 top_k cpp 复现代码：`，再用上面的 `<details>` 折起，作为文章的最后一块收尾。关键函数或类写完整、能独立看懂即可，不必是整份工程文件；代码的位置和后来的变化只用泛化说法交代，不写内部路径和模块名。
- 长日志可以直接贴出，但只保留定位问题需要的行；错误类型、行号和栈深这些定位信息不改写，内部符号按下面的「不能出现的内容」脱敏。
- 不编造数据。只有用户提供过 benchmark、运行日志或测试结果时，才写具体耗时、吞吐、文件大小和线程数量。

## 不能出现的内容

下面这些一律不写进文章，正文、行内代码、代码注释和贴出的日志都算：

- 内部文件路径、目录和文件名，例如带真实模块层级的 `模块目录/子模块/实现文件.h`。
- 带项目语义的模块名、命名空间和类名，例如 `内部前缀Foo`、`内部命名空间::子模块`。
- 公司、团队、产品、仓库名，客户与同事姓名，工号，内网域名和 IP。
- 内部数据结构、表名、行情字段名、因子编号和其他业务口径。

需要交代代码位置或后来的变化时用泛化说法，例如“后来单独拆成了一个头文件”“当时写在一个公共头文件里”，不写具体路径和模块名。

贴原始日志或崩溃栈时保留错误类型、行号、栈深这些定位信息，内部符号换成中性的占位名称，例如把 `内部类::方法名` 写成 `FactorWriter::write`；拿不准某个名字算不算内部时，一律用泛化写法。涉及的内部模块层级太多、脱敏之后不成形时，不贴原始片段，直接用文字描述这段日志或调用栈说了什么。

## 排版

- 默认只有 H1，不写二级章节。
- 连续叙述使用普通段落，不把每一句话拆成项目符号。
- 技术名词和代码使用行内代码；少用粗体。
- 不使用 ✅、❌、🚀 等 emoji，不做勾叉清单。
- 避免 ASCII 架构图、复杂表格和只有形式感的流程框。
- 正文里的数学量（变量、下标、索引、常量）和阿拉伯数字都写成 LaTeX 行内公式 `$...$`，与相邻的中文、字母、数字之间留一个空格（例如 `这是 $a_{i}^{10}$ 正文`、`取 $k = 10$`、`前 $10$ 个`、`退出码是 $139$`），与标点和括号之间不加空格（`$k$，`、`（$k$）`）。量纲词留在公式外：`$6$ GB`、`$2473$ 万行`。
- 版本号（`CentOS 7.9`、`GCC 12.2.0`、`Arrow/Parquet 21.0.0`）和十六进制字面量（`0x1420`）保持普通文本，不套 `$...$`。
- 公式内部的运算符按 LaTeX 习惯留空格，写 `$k = 10$` 而不是 `$k=10$`。
- 库名、工具名、语言名和缩写保持普通文本或反引号（polars、py、C++、gdb、ASAN、DSO），不进公式；函数名、类型名、文件名和错误信息这些代码标识符继续用反引号。
- 算法叙述里的数组引用写成下标形式：`v[0]` 写成 `$v_{0}$`，`v[i]` 写成 `$v_{i}$`；半开区间写成 `$v_{1} \sim v_{len-1}$`，`v[0..10)` 写成 `$v_{0} \sim v_{9}$`；连续几项写成 `$a, a+1, a+2$`。
- 公式里不写 `/` 和 `*`：除法用 `$\frac{\text{len}}{12}$`，乘法用 `$\times$`，例如 `$v_{\frac{\text{len}}{8} \times 4}$`。路径、命令行参数和 API 调用里的 `/` 不是除法，仍按原样放在行内代码里。
- 代码里的条件与赋值也可以写进公式：`index == len - 1` 写成 `$\text{index} = \text{len} - 1$`，`len <= 16` 写成 `$\text{len} \le 16$`，`frac = 83` 写成 `$\text{frac} = 83$`。
- 变量名一律写进公式，出现在正文里但没加任何标记的也要改：单字母直接写（`$i$`、`$a$`），多字母用 `\text{}` 保持直立（`$\text{frac}$`、`$\text{pivot}$`、`$\text{numLt}$`），避免渲染成斜体字母串。类型名、库名和数据字段名（double、polars、tick、qty）保持普通文本。
- 关键字和单独提到的运算符也写进公式：`if` 写成 `$\text{if}$`，`return` 写成 `$\text{return}$`，`try/catch` 写成 `$\text{try}/\text{catch}$`，比较关系从 `>` 换成 `>=` 写成从 `$>$` 换成 `$\ge$`。
- 函数名、API 调用、命名空间名和文件名用行内代码，不进公式；类型名和字面量（`const char*`、`void*`、`true`、`nullptr`）也保持在行内代码里。
- 反引号里的代码、代码块、标题、路径和文件名里的数字保持原样，不套 `$...$`。
- 块级推导只在确有必要时展开，不为了显得严谨而堆公式。

## 明确避开 AI 味

- 不写“根因如下”“修复方案”“验证结果”“不影响范围”“核心收获”“经验教训”等固定栏目。
- 不连续使用“首先、其次、最后”“一方面、另一方面”“不仅、而且”这类模板连接词。
- 不写“值得注意的是”“需要强调的是”“综上所述”“由此可见”等空转句。
- 不把内容强行排成三个并列短句，也不反复使用“不是……而是……”制造金句感。
- 不写“综上所述，这个方案兼顾了……”“希望这篇文章能帮助到你”之类结尾。
- 不在每段后补一句解释上一句的废话。

## 收尾方式

文章可以在验证结果、剩下的疑点或一个补充做法处自然结束。常见收尾是：

- 简短说明现在的实现状态。
- 留下尚未完全解释清楚的问题。
- 给出另一个可行做法。
- 用删除线补一句真实感想。

不要为了完整而补一个概括全文的总结。
