# 常见记录骨架

这些只是组织材料的方式，不要把标题直接写进文章。现有博客通常是一篇一个问题，正文用连续段落展开。

算法和优化类文章用小标题把下面的步骤切成几节，每个标题写清这一节在讲什么（`整体求和序`、`块间递归`、`抛开对齐看复杂度`），不编号、不用栏目名。debug 记录通常保持单 H1 连续叙述。

## Debug

适合复现、日志、崩溃、偶发错误、线程问题和环境差异。

推荐顺序：

1. 用一两句话写清现象，能贴原始报错就贴原始报错。
2. 写最初怀疑的机制和已经做过的修改。
3. 写删除修改、增加日志或换一种实现后的结果。
4. 回到源码或调用链，说明哪条证据推翻了之前的判断。
5. 写最终修改和能够确认的验证结果。
6. 如果还有没查清的部分，直接留下，不补一个完美结论。

如果排查过程中换了一套新算法，先按 `SKILL.md` 的定位确认步骤问清这篇到底按 debug 写还是按新算法写，再决定用这个骨架还是下面的算法骨架。

开场示例：

```markdown
# 在容器内跨 DSO 加载时的符号解析表现

fmtlog，DSO，符号可见性。

程序启动后会先输出两行工作线程绑核日志，接着直接 `free(): invalid pointer`。
```

## 优化

适合缓存、批处理、数据布局、编译选项和性能回退。标题用「基于 xxx 的 xxx 做法」，或者写清在什么条件下表现如何。

推荐顺序：

1. 写旧实现和可观察到的瓶颈。
2. 写为什么当前路径重复做了工作，或者为什么无法直接并行。
3. 写优化思路和实现，只贴改变行为的关键代码，每个关键步骤配一小段。
4. 写正确性边界，例如顺序、精度、内存所有权和线程安全。
5. 有推导价值时写和常规做法的复杂度对比，总量、深度、误差和内存访问分开算。
6. 写适用场景：什么规模下划算，什么规模下分层的固定开销超过收益，不同硬件形态的取舍差在哪。
7. 有真实数据时再写优化前后的数据。编译和运行按 `SKILL.md` 的编译验证步骤记四项：在哪编、编译器与版本、标准、结果；每个程序后面跟一行编译环境。

开场通常可以直接写：

```markdown
原来的实现每次都会重新遍历一遍整张表，数据量大之后这里就成了主要耗时。
```

## 算法

适合工作中遇到的匹配、调度、压缩、图算法和小规模组合问题。

推荐顺序：

1. 写问题转化后的核心观察。
2. 说明为什么贪心、二分、动态规划或数据结构能够成立。
3. 写转移、维护量或容易漏掉的边界。
4. 写实现细节，观察、推导和关键代码对齐到具体几行。
5. 写和常规做法的复杂度对比，把推导的前提和成立的规模范围写清楚。复杂度、误差和边界结论先用联网工具核对来源，并自己独立推一遍；引用按 `style-profile.md` 的「引用与外部资料」处理，找不到来源的按猜测语气写。
6. 写适用场景：这套做法适合什么规模、什么数据特征，什么时候不如直接写朴素版本。编译和运行按 `SKILL.md` 的编译验证步骤记四项：在哪编、编译器与版本、标准、结果；每个程序后面跟一行编译环境。

开场通常可以直接写：

```markdown
考虑固定右端点，左端点满足条件时一定是一段连续区间。
```

## 多个方案

如果确实有两个值得保留的做法，可以按现有博客里的方式写：`解法一`、`解法二`，或者“也可以……”放在正文后面。不要为了显得完整而强行拼出多个方案。

## 完整实现的位置

优化、算法和 debug 记录，如果代码已经有比较完整的解决或实现方案，可以在正文之后补一份完整实现：引导语只写清是什么代码，直接写成 `完整的 top_k cpp 复现代码：`，后面接 `<details>` 折叠块或代码块，作为文章的最后一块结束，后面不再接总结。关键函数或类写完整、能独立看懂即可，不必是整份工程文件。

不要用“后来单独拆成了一个头文件”这类句子给完整实现做过渡，也不要在正文里专门交代代码搬去了哪里。只有代码位置本身影响理解时才用一句泛化说法，内部路径、模块名和类名按 `style-profile.md` 的「不能出现的内容」处理，一律不写进文章。

竞赛题解本来就在每道题后面接完整代码，最后一题的代码块直接收到文件结尾，这一类不额外加引导语。
