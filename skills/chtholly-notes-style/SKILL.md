# C++ 工作笔记

把 C++ 工作中的优化、算法和 debug 记录写成用户大学时期博客的风格。目标不是套一个“程序员博客模板”，而是保留问题推进过程、个人判断和适度口语，让文章看起来确实由本人整理过。

写作前先读 [references/style-profile.md](references/style-profile.md)。需要判断文章骨架或开头时，再读 [references/entry-patterns.md](references/entry-patterns.md)。

## 工作流

1. 先核对原始材料：日志、源码、diff、测试结果和用户描述。没有证据的根因、失败过程、性能数字和验证结果不要补写。
2. 区分三类信息：确定现象、能由源码支持的机制、仍未闭环的猜测。后两类要明确语气，不能写成确定结论。
3. 找到文章唯一的主线。debug 写问题如何被逐步缩小，优化写旧做法为什么不够以及新做法的代价，算法写关键观察和实现细节。
4. 用连续叙述推进，先写现象或最初想法，再写尝试、发现、修改和验证。失败尝试和不成立的猜测通常可以保留。
5. 代码只保留支撑结论的部分。长代码或大段日志用 `<details>` 折起，`<details>` 与 `<summary>点击查看代码</summary>` 分两行写；短日志和关键源码直接放在正文。
6. 优化、算法或 bug 记录，如果相关代码已经有比较完整的解决或实现方案，在正文写完后附一份完整实现：先写一句朴素引导语，例如“完整的 top_k cpp 复现代码：”，再接一个 `<details>` 折叠块。关键函数或类写完整、能独立看懂即可，不必是整份工程文件；代码还在改或只剩片段就不要附，也不为了看起来完整而补代码。
7. 写完后检查是否出现报告式标题、空泛总结、整齐排比、过量粗体、emoji、勾叉和没有证据的“最佳实践”。

## 输出约定

- 不写项目内部信息：内部文件路径和目录、模块名、命名空间、类名，公司／团队／产品／仓库名，客户与同事姓名、工号、内网域名和 IP，以及内部数据结构与业务字段。需要交代代码位置或后来的变化时只用泛化说法，贴日志时内部符号要脱敏，完整清单见 [references/style-profile.md](references/style-profile.md) 的「不能出现的内容」。
- 正文使用中文，技术名词、函数名和错误信息保留原文。
- 正文里的数学量（变量、下标、索引、常量）和阿拉伯数字都写成 LaTeX 行内公式，与相邻的中文、字母、数字之间留一个空格，与标点和括号之间不加空格，例如 `这是 $a_{i}^{10}$ 正文`、`前 $10$ 个`、`退出码是 $139$`、`$k$，`；量纲词留在公式外，写成 `$6$ GB`、`$2473$ 万行`。公式内部的运算符也留空格，写 `$k = 10$`。版本号（`CentOS 7.9`、`GCC 12.2.0`）和十六进制字面量（`0x1420`）保持原样；库名、工具名、语言名和缩写保持普通文本或反引号，不进公式；代码标识符、代码块、标题、路径和文件名里的数字也保持原样。
- 算法叙述里的下标、区间、算式、条件和赋值都写成公式：`v[0]` 写 `$v_{0}$`，`v[1..len)` 写 `$v_{1} \sim v_{len-1}$`，`a, a+1, a+2` 写 `$a, a+1, a+2$`，除法用 `\frac{}{}`、乘法用 `\times`。
- 变量名、关键字和单独提到的运算符一律写成公式，正文里裸写的也要改：单字母写 `$i$`，多字母用 `\text{}` 保持直立（`$\text{pivot}$`、`$\text{if}$`、`$\text{sizeof}$`），`>`、`>=` 写 `$>$`、`$\ge$`。函数名、API 调用、类型名和文件名用行内代码，不进公式。
- H1 直接写问题、算法或优化主题，下一行给一个简短标签，不写“排查记”“深入理解”“一文搞懂”等标题包装。
- 文件名为 `主题.md`。
- 默认不使用二级标题，不生成目录、背景介绍和总结章节。
- 不写“根因如下”“修复方案”“验证结果”“不影响范围”等模板段落。
- 对已经更新的代码，明确使用“当时”“后来改成”等时间语气，不假装仍能复现旧实现。
- 不为了口语化编造错误、对话、心路历程或删除线内容。

如果用户只给了一段工作记录，内容不足以判断根因或效果，直接按现有证据成文并把未确定处写清楚，不要向用户索取可以在仓库中查到的信息。
