# C++ 工作笔记

把 C++ 工作中的优化、算法和 debug 记录写成用户大学时期博客的风格。目标不是套一个“程序员博客模板”，而是保留问题推进过程、个人判断和适度口语，让文章看起来确实由本人整理过。

写作前先读 [references/style-profile.md](references/style-profile.md)。需要判断文章骨架或开头时，再读 [references/entry-patterns.md](references/entry-patterns.md)。

## 工作流

1. 先核对原始材料：日志、源码、diff、测试结果和用户描述。没有证据的根因、失败过程、性能数字和验证结果不要补写。需要查外部资料时优先一手来源，例如语言与库的规范、官方文档、编译器或运行时的问题报告，二手教程只当线索。要验证代码时先探本机工具链，有编译器就在本机编，没有才转到在线服务。
2. 记录算法、数据结构或某个知识点这类科普性内容时，动笔前必须先用联网工具查一遍，确认要写的内容站得住：
   - 查什么：这套做法的来源和原始定义、能写进正文的复杂度与误差结论、容易记错的边界和限制条件，以及它和相邻做法的区别。凭印象写下的复杂度或结论一律先去核对。
   - 优先找一手来源：论文原文、标准或规范、官方文档、源代码和 changelog、编译器或运行时的问题报告。OI-Wiki、CP-Algorithms、厂商技术博客这类整理性资料用来交叉印证，不作为唯一依据。
   - 动手前先自己算一遍，再拿来源比对：总操作量、关键路径、误差界各用自己的推导核对。对不上时先查自己的假设错在哪，不为了和引用一致而改结论。
   - 结论只写来源实际说了什么。只找到低可信度资料、或者几份资料互相矛盾时，按「区分三类信息」那条当猜测写，并在交付说明里列出哪几条没有核实。
3. 动笔前先把定位定下来，它决定主线，不能等成文之后再补。材料里出现优化，或者修 bug 时换了一套和常规做法不同的算法，先用 `ask_user_question` 确认这篇按哪种写：
   - 用户说明是针对项目中某个方法的优化记录时，按优化记录写：先写旧做法和可观察到的瓶颈，再写新做法、正确性边界以及性能或行为上的代价。
   - 材料本身就是排查过程时，按 debug 记录写：保留“现象、怀疑、失败尝试、源码证据、结论”的推进顺序。
   - 其余情况默认按“介绍一种优化/算法方式”写：正文围绕这套做法怎么成立、代价在哪里展开，不写旧实现和改造历程，也不按排查顺序推进。
   分辨不出该用哪种时直接问，不要自己猜。只是改参数、调顺序而没有引入新算法的情况不用问。
4. 区分三类信息：确定现象、能由源码支持的机制、仍未闭环的猜测。后两类要明确语气，不能写成确定结论。
5. 找到文章唯一的主线。debug 写问题如何被逐步缩小；优化记录写旧做法为什么不够以及新做法的代价，介绍一种做法本身时写这套做法怎么成立、代价在哪里；算法写关键观察和实现细节。
6. 用连续叙述推进，先写现象或最初想法，再写尝试、发现、修改和验证。失败尝试和不成立的猜测通常可以保留。
7. 算法和优化类文章用小标题分段，每个标题直接写这一节在讲什么，例如 `整体求和序`、`块间递归`、`抛开对齐看复杂度`。不编号，也不写“背景介绍”“方案对比”“总结”这类只有形式的栏目名；一节只承载一个判断或一段实现，节数按内容定，不为了对称凑标题。短小的 debug 记录保持单 H1，用连续段落推进。
8. 每个关键步骤写成“文字说明 + 对应代码”的形式。先说这一步要解决什么、判断是什么，再贴支撑这个判断的那段代码，让读者能把推导和实现对齐到具体几行，不要只丢一大段代码让人自己找。一屏以内的短代码直接放在正文，不上折叠；长代码和大段日志用 `<details>` 折起，`<details>` 与 `<summary>点击查看代码</summary>` 分两行写。
9. 介绍算法或与常规做法不同的实现时，如果有推导价值，就把复杂度和优缺点讲清楚：总操作量、依赖深度（最长加法链或关键路径）、误差界、内存访问各算一遍，和常规做法放在一起比。成立的前提要写明，例如 $n$ 是否是块长的整数倍、pivot 是否接近真实中位数、有没有开 `-ffast-math`；渐近量级和常数分开说，不要把某个规模的实测值当成渐近结论。单独成行的推导和结论用 `$$ ... $$`。写完回头通读一遍，检查有没有把总操作量和关键路径混在一起、有没有把一步推导的假设套到不适用的数据上；没想通的地方直接写“这里还没推明白”，不补一个看起来完整的结论。
10. 算法和优化类文章在复杂度和误差之后、完整实现之前，加一节写适用场景：什么规模下这套做法划算，什么规模下分层的固定开销超过收益，算子或数据结构需要满足什么性质，不同硬件形态下的取舍差在哪。边界要写到能据此判断用不用，不写“视情况而定”。
11. 需要跑代码验证时先探本机工具链（`g++ --version`、`clang++ --version`、`wsl.exe -l -v`，Windows 上再看 `cl.exe`、`vswhere.exe` 以及 MSYS2、LLVM、VS Build Tools 的常见位置）：本机有编译器就在本机编，记下编译器和版本；没有才用在线服务。投给在线服务的代码当成公开内容，内部代码、真实数据和内网符号一律不投。
    在线编译用 Wandbox 的 `api/list.json` 和 `api/compile.json`：`api/list.json` 列出可用编译器和每个编译器接受的开关名，`api/compile.json` 提交 `compiler`、`code`、`options`、`stdin` 四个字段，`options` 是逗号连接的开关名列表。每换一个环境先编一个打印 `__cplusplus` 的小程序确认标准真的生效，因为 `options` 里不认识的名字会被静默忽略；一批不要超过三个，出现 `fetch failed` 是退避重试而不是编译失败；编译失败看 `status` 和 `compiler_error`，不是 HTTP 错误。每次验证至少记四项：在哪编、编译器与版本、标准、结果。没实跑过的代码不写成跑过，也不补“已通过”。
12. 优化、算法或 bug 记录，如果相关代码已经有比较完整的解决或实现方案，在正文写完后附一份完整实现。引导语只写清是什么代码，直接写“完整的 xxx 实现：”，不写“这个实现后来单独放进了一个头文件，只做这一件事”这类交代代码去向的过渡句，后面接 `<details>` 折叠块或代码块。关键函数或类写完整、能独立看懂即可，不必是整份工程文件；代码还在改或只剩片段就不要附，也不为了看起来完整而补代码。
13. 写完后检查是否出现报告式标题、空泛总结、整齐排比、过量粗体、emoji、勾叉和没有证据的“最佳实践”；同时检查脚注闭合的 `]` 后是否留了空格，以及程序和输出有没有跟所属的那条编译环境说明、有没有把没跑过的代码写成跑过、有没有把验证流程当成正文写出来。

## 输出约定

- 不写项目内部信息：内部文件路径和目录、模块名、命名空间、类名，公司／团队／产品／仓库名，客户与同事姓名、工号、内网域名和 IP，以及内部数据结构与业务字段。需要交代代码位置时只用泛化说法，而且只在这一点确实影响读者理解时提一句，不专门交代代码后来搬到了哪里；贴日志时内部符号要脱敏，完整清单见 [references/style-profile.md](references/style-profile.md) 的「不能出现的内容」。
- 正文使用中文，技术名词、函数名和错误信息保留原文。
- 正文里的数学量（变量、下标、索引、常量）和阿拉伯数字都写成 LaTeX 行内公式，与相邻的中文、字母、数字之间留一个空格，与标点和括号之间不加空格，例如 `这是 $a_{i}^{10}$ 正文`、`前 $10$ 个`、`退出码是 $139$`、`$k$，`；量纲词留在公式外，写成 `$6$ GB`、`$2473$ 万行`。公式内部的运算符也留空格，写 `$k = 10$`。版本号（`CentOS 7.9`、`GCC 12.2.0`）和十六进制字面量（`0x1420`）保持原样；库名、工具名、语言名和缩写保持普通文本或反引号，不进公式；代码标识符、代码块、标题、路径和文件名里的数字也保持原样。
- 算法叙述里的下标、区间、算式、条件和赋值都写成公式：`v[0]` 写 `$v_{0}$`，`v[1..len)` 写 `$v_{1} \sim v_{len-1}$`，`a, a+1, a+2` 写 `$a, a+1, a+2$`，除法用 `\frac{}{}`、乘法用 `\times`。
- 变量名、关键字和单独提到的运算符一律写成公式，正文里裸写的也要改：单字母写 `$i$`，多字母用 `\text{}` 保持直立（`$\text{pivot}$`、`$\text{if}$`、`$\text{sizeof}$`），`>`、`>=` 写 `$>$`、`$\ge$`。函数名、API 调用、类型名和文件名用行内代码，不进公式。
- 单独成行的公式用 `$$ ... $$`，前后各留一个空行，让它居中显示，不再用反引号或裸文本包推导；行内公式继续用 `$ ... $`。只有关键等式、递推式和复杂度结论才单独成行，正文里出现的量、下标和单个变量留在行内。
- H1 直接写问题、算法或优化主题，下一行给一个简短标签，不写“排查记”“深入理解”“一文搞懂”等标题包装。标题不写“xxxx：xxxxx”的冒号格式，简要说明即可：算法和知识点类文章直接用算法或技术名（`# SIMD`、`# PairWise`），有明确中文名时写「英文|中文」（`# PairWise|成对求和`）；针对某种做法的优化用「基于 xxx 的 xxx 做法」，debug 记录写清在什么条件下出问题，例如 `# 在容器内跨 DSO 加载时的符号解析表现`。不写成“某某对不上排查”。
- 文件名为 `主题.md`。
- 涉及算法、数据结构或知识点的结论要先在正文里对得上来源：能在正文里对照的就用内联脚注，只用来说明出处、不改变叙述的信息放在交付说明里。结论和来源对不上、或者找不到来源时，按猜测语气写，不当成确定结论。
- 引用外部资料用内联脚注 `^[引用内容]`，脚注里只放 URL，闭合的 `]` 后留一个半角空格再接文字或标点；同一个序号不能复用，一条内容对应多个链接时拆成相邻的两个脚注。不设末尾的参考文献节，细节见 [references/style-profile.md](references/style-profile.md) 的「引用与外部资料」。
- 不生成目录，不写背景介绍和总结章节。
- 不写“根因如下”“修复方案”“验证结果”“不影响范围”等模板段落。
- 编译环境按文章分层标注，不逐段重复：整篇环境一致就只在开头标一次；一篇里有多种环境按节归并，写在节首（大节一致写在大节，小节一致写在小节）；节里个别程序换了标准或编译器的，只给那一段单独标一句。每处标注写清在哪编、编译器和版本、标准、结果。
- 本机编的写“本地”，例如 `编译环境：本地 g++ 13.2.0，-std=gnu++20。`；在线编的写明站点，例如 `本节代码：Wandbox 在线编译，gcc-13.2.0，-std=gnu++2a。`。程序后面紧跟的输出或报错跟着它所属的那条环境说明，不再单独标。这个结果只代表该编译器版本加该标准，不当成本机或线上工具链的结论；诊断里的服务端临时文件名不能当成本地目录结构。
- 编译环境按事实写：直接写“文中验证环境：Wandbox 在线编译，gcc-13.2.0，-std=gnu++2a。”这种陈述，不解释为什么用在线服务、不写“本机没有编译器所以……”“先探本机工具链”这类交代验证流程的话。验证规矩本身不是文章内容；报错和输出是这些环境上的原文，也不必声明。
- 在线诊断引用前清掉 ANSI 颜色码，`compiler_message` 常和 `compiler_error` 重复，去重后再引用。
- 对已经更新的代码，明确使用“当时”“后来改成”等时间语气，不假装仍能复现旧实现。
- 不为了口语化编造错误、对话、心路历程或删除线内容。

如果用户只给了一段工作记录，内容不足以判断根因或效果，直接按现有证据成文并把未确定处写清楚，不要向用户索取可以在仓库中查到的信息。
